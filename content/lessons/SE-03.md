## 从业务约束识别主键、外键和联系

数据库题先把业务规则翻译成约束，再选表结构。**候选键 Candidate key** 是能唯一确定一行的最小属性集合；从候选键中选定一个作为主键。能唯一确定但含多余属性的集合只是超键。

假设课程平台中：每个学生有唯一 student_id；每门课有唯一 course_id；同一学生对同一门课只保留一条选课记录。

| 表 | 属性 | 主键 |
| --- | --- | --- |
| Student | student_id, student_name | student_id |
| Course | course_id, course_name | course_id |
| Enrollment | student_id, course_id, score | (student_id, course_id) |

一个学生可选多门课，一门课可被多个学生选择，属于多对多联系。Enrollment 中两列同时标识一次选课，score 是这次联系的属性，不应放在 Student 表里。

Enrollment.student_id 引用 Student.student_id，course_id 引用 Course.course_id，构成外键。主键要求唯一且非空；外键主要保证引用完整性，不等于“本列不能重复”。多名学生选同一门课时，Enrollment.course_id 当然重复。

若业务允许重修并保存每次成绩，原来的二列组合不再唯一，需要加入学期/次数等能区分事件的属性，或使用独立事件编号并另设业务唯一约束。不能不读条件就套用“多对多永远只有两个字段作键”。

**自查：** 对一对多的“部门—员工”，通常把部门编号作为外键放在员工表中。若每个员工必须有部门，除外键外还需 NOT NULL 等约束表达“必须”。

## 函数依赖与属性闭包：用推导找候选键

`X → Y` 表示：在所有满足业务规则的合法数据中，只要两行的 X 相同，Y 就必须相同。它是约束，不是仅凭当前几行样本碰巧无重复就能断定。

设关系 R(A,B,C,D)，仅给定函数依赖 `A→B、B→C、AC→D`。求 A 的**属性闭包 A⁺**：

1. 从 {A} 出发。
2. 由 A→B 得 {A,B}。
3. 由 B→C 得 {A,B,C}。
4. 此时已包含 A 和 C，由 AC→D 得 {A,B,C,D}。

A 能确定全部属性，且单属性不能再删，所以 A 是候选键。AC 也能确定全部属性，但含多余 C，只是超键。这个例子说明“出现在复合依赖左侧”不代表必须放进候选键。

再看 R(A,B,C)，仅有 `AB→C`。A⁺只有 A，B⁺只有 B，(AB)⁺才覆盖全部，因此候选键为 AB。判断最小性需要检查删去任一属性后是否仍可决定全部。

**依赖推导与更新异常的关系：** 假设员工表包含 employee_id、department_id、department_name，规则为 employee_id→department_id、department_id→department_name。同一部门名重复存很多次；只修改部分行，就可能出现同部门多个名字。

本单元使用的依赖集合均明确给出。真实设计时，先确认业务约束再求闭包，不能凭字段名字想当然。

## 范式与分解：不要只背 1NF、2NF、3NF

本课默认属性值满足 1NF 的原子性要求。**主属性** 指出现在任一候选键中的属性，其余是非主属性。

- 2NF：每个非主属性完全依赖于每个候选键，不依赖键的真子集。
- 3NF：对每个非平凡依赖 X→A，X 是超键，或 A 是主属性。
- BCNF：对每个非平凡依赖 X→Y，X 必须是超键。它比 3NF 更严格。

例：R(student_id, course_id, student_name, course_name, score)，依赖为 student_id→student_name，course_id→course_name，(student_id,course_id)→score，且无其他独立依赖。候选键是 (student_id,course_id)。两个名字各自依赖键的一部分，因此只有 1NF，不满足 2NF。

分解成 Student(student_id, student_name)、Course(course_id, course_name)、Enrollment(student_id, course_id, score)，使名字和成绩分别放在真正决定它们的键下面。

另一个例子：Employee(employee_id, department_id, department_name)，依赖 employee_id→department_id、department_id→department_name。唯一候选键是 employee_id，无复合键的部分依赖问题；但部门名经由非键属性传递依赖于员工号，达到 2NF、未达到 3NF。

分解为 Employee(employee_id,department_id) 和 Department(department_id,department_name)。公共属性 department_id 能决定 Department 的全部属性，按无损二元分解判据，这次分解可无损连接；两条原依赖也能分别在各表中检查。

**无损连接不等于随便拆表。** 例如 R(A,B,C) 只有 AB→C，拆成 AB 与 BC，公共 B 不能决定任一子表全部属性，不能保证无损。两行 (1,x,p)、(2,x,q) 投影后再连接，会额外产生 (1,x,q)、(2,x,p)。

练题顺序：写候选键 → 标主属性 → 检查依赖 → 判断范式 → 检查分解。不要仅凭“出现传递”两个字就选答案。

## 案例建模与 SQL：把约束落实到表和查询

案例：训练营有学员与课程；每个学员可以加入多门课程；每门课程可被多位学员加入；每对学员—课程只保留一条记录，并记录成绩。先识别实体 Student、Course，再用 Enrollment 表承载多对多联系，主外键与前一小节一致。

若新增“每次考试都记录日期和成绩”，不能直接在原表里堆 exam1、exam2 列。需要描述考试事件，如 Attempt(attempt_id, student_id, course_id, exam_date, score)，并明确它引用哪一次选课以及重复尝试规则。新的业务条件会影响键，不是简单增一个文本字段。

**SQL 连接** 用外键对应条件将相关行组合。JOIN ... ON 表示连接条件；WHERE 过滤行；GROUP BY 把行分组；聚合后用 HAVING 过滤组。

```sql
SELECT s.student_name, c.course_name, e.score
FROM Student AS s
JOIN Enrollment AS e ON e.student_id = s.student_id
JOIN Course AS c ON c.course_id = e.course_id
WHERE e.score >= 80;
```

注意两个 ON 解决的是“哪些行属于同一对象/事件”，不是分数筛选。忘记连接条件可能把无关行组合，不能靠最终行数看起来正常就认为正确。

“列出至少有 2 位学员选修的课程编号”：

```sql
SELECT course_id, COUNT(*) AS learner_count
FROM Enrollment
GROUP BY course_id
HAVING COUNT(*) >= 2;
```

这里因为每对学员—课程只有一行，COUNT(*) 才等于学员数。若表保存多次考试，则可能需要 COUNT(DISTINCT student_id)，不能无视表的粒度照搬。

**保留无选课的学员** 用 LEFT JOIN。例：Student LEFT JOIN Enrollment，再按学生分组，计数应使用 COUNT(e.course_id)，而不是 COUNT(*)；无匹配时补出的那行 course_id 为 NULL，前者计为 0，后者会计为 1。

案例作答要同时写出表、键和原因。只写“创建关联表”而不给字段与约束，尚不足以证明完成了设计。
