# 对象、类与设计原则

> 代码基线：C++17；UML 记法按 UML 2.5.1。后续版本特性会明确标注，本节不依赖未指定行为。

## 考查目标

能够准确识别对象、类与设计原则中的角色、约束与边界；能从题干材料推导唯一结论，并说明结论成立的前提。

## 必要概念

对象把状态与维护该状态不变式的操作封装成一个责任边界。类是对象的类型描述；抽象关注可观察契约，封装控制表示细节。高内聚意味着同一类成员服务于同一变化原因，低耦合意味着协作者只依赖必要接口。SOLID 可作为诊断词汇：SRP 看变化原因，OCP 让新增行为通过扩展完成，LSP 要求子类型不破坏基类可观察契约，ISP 避免客户依赖不用的方法，DIP 让高层策略依赖抽象。

## 原理与条件

评价类设计要从“不变式由谁维护”和“哪个需求变化会修改此类”入手。封装不是把字段一律设为 private，而是禁止客户绕过保持不变式的操作。SRP 的变化原因必须具体到角色或规则；OCP 通过稳定抽象形成扩展点；LSP 检查子类型是否加强前置条件、削弱后置条件或破坏不变式；ISP 检查具体客户是否被迫依赖不用的操作；DIP 检查高层策略是否直接依赖易变细节。

把订单金额非负写成 Checkout 的后置条件后，任一 DiscountPolicy 都必须保持该条件。若新策略可能算出负值，应在策略契约或 Checkout 校验处处理，不能因“实现了接口”就视为可替换。依赖方向可从构造函数类型判断：`Checkout(DiscountPolicy&)` 依赖抽象；`Checkout(VipPolicy&)` 仍与具体策略耦合。

## 推导例题

订单折扣若用不断增长的 if(type) 分支，新增会员会修改结算器。定义 DiscountPolicy::apply(total)，RegularPolicy 与 VipPolicy 实现接口，Checkout 只持有策略引用。结算器的变化原因收敛为流程变化，折扣变化落在策略实现；这同时体现 OCP 与 DIP。若 VipPolicy 返回负金额，则虽类型兼容却破坏‘结果非负’的后置条件，违反 LSP。

推导时先列 Checkout 的稳定流程与折扣算法的变化原因，再写接口前置/后置条件，最后用“新增一种会员是否修改 Checkout”和“任一策略是否保持金额非负”两问复核 OCP 与 LSP。

## 易错点与反例

1. 把一个大类拆成多个同样共享全局状态的小类，并没有降低耦合，也没有形成清楚责任。
2. 认为“子类增加检查总更安全”。若基类允许的输入被子类拒绝，就是加强前置条件并破坏替换。
3. 在 C++ 输出题中忽略对象切片、析构顺序、异常展开或迭代器失效。若片段含未定义行为，就不能声称有确定输出。
4. 看到包装结构就一律回答装饰器。必须以转换接口、增加职责或控制访问的意图区分适配器、装饰器和代理。
