# 结构型设计模式

> 代码基线：C++17；UML 记法按 UML 2.5.1。后续版本特性会明确标注，本节不依赖未指定行为。

## 考查目标

能够准确识别结构型设计模式中的角色、约束与边界；能从题干材料推导唯一结论，并说明结论成立的前提。

## 必要概念

结构型模式通过组合类和对象形成更大结构。适配器转换不兼容接口；装饰器保持同一组件接口并在转发前后增加职责，可层叠；外观为复杂子系统提供简化入口，但不禁止高级客户直达子系统；代理也保持主题接口，却主要控制访问、延迟创建或远程通信。区分装饰器与代理要看意图：前者扩展职责，后者控制访问。

## 原理与条件

适配器拥有 Target 接口并把请求转换给 Adaptee；装饰器与 Component 同接口，持有另一个 Component 并在转发前后附加职责；代理也实现 Subject 接口，但重点是延迟、权限、远程或缓存等访问控制；外观提供新的粗粒度入口协调多个子系统。结构相似时必须用意图区分。

C++ 可用 `unique_ptr<Component>` 建立独占装饰链，抽象 Component 需要虚析构。调用从最外层进入真实组件，返回值从内向外逐层包装；析构从最外层开始递归释放。适配器若只是借用旧对象可持引用，若拥有旧对象则应让所有权类型明确表达。

## 推导例题

旧温度库返回华氏度 legacy.readF()，业务需要 CelsiusSensor::readC()。FahrenheitAdapter 持有 legacy 并在 readC 中计算 (f-32)*5/9，这是适配器。若再用 LoggingSensor 包住任意 CelsiusSensor，在调用前后记录日志且仍暴露 readC，则是装饰器。若 RemoteSensorProxy 在首次调用时建立连接并校验权限，则是代理。三者结构相似，职责不同。

温度例先确认新旧接口不兼容，从而选适配器并写换算；日志层保持相同 readC 接口且增加行为，判为装饰器；远程层控制连接和权限，判为代理。三个结论来自意图而非都“包了一层”。

## 易错点与反例

1. 看到包装类就答装饰器，忽略它实际转换接口或控制访问。
2. 装饰链各层都用 shared_ptr，即使所有权是严格单链，徒增共享语义与环风险。
3. 在 C++ 输出题中忽略对象切片、析构顺序、异常展开或迭代器失效。若片段含未定义行为，就不能声称有确定输出。
4. 看到包装结构就一律回答装饰器。必须以转换接口、增加职责或控制访问的意图区分适配器、装饰器和代理。
