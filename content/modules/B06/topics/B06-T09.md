# 行为型设计模式

> 代码基线：C++17；UML 记法按 UML 2.5.1。后续版本特性会明确标注，本节不依赖未指定行为。

## 考查目标

能够准确识别行为型设计模式中的角色、约束与边界；能从题干材料推导唯一结论，并说明结论成立的前提。

## 必要概念

行为型模式分配算法和协作职责。策略封装可替换算法，由上下文显式选择；状态把行为随内部状态改变的规则分散到状态对象，迁移通常由上下文或状态控制。观察者建立一对多通知，需明确订阅注销和观察者生命周期；命令把请求封装为对象，便于排队、日志、撤销。选择模式应写出 Context、抽象角色、具体角色与调用方向，而不是只凭动词猜名称。

## 原理与条件

策略把一组等价算法置于 Strategy 接口后，由 Context 委托；状态模式也委托，但当前 State 代表上下文内部阶段，事件推动迁移。观察者由 Subject 管理订阅并向多个 Observer 发布变化，必须定义退订、失效观察者和通知中修改订阅表的语义。命令把请求、Receiver 和撤销数据封装为对象，Invoker 只安排执行。

C++ 实现观察者时，可用 RAII 订阅令牌自动注销，或保存 weak_ptr 并在通知时 lock；遍历快照可避免回调退订导致迭代器失效。命令历史应在 execute 成功后提交 unique_ptr，失败命令不能进入“已执行”历史。策略与状态抽象基类若经接口指针销毁，同样需要虚析构。

## 推导例题

编辑器将 Command 放入历史栈。InsertCommand::execute 插入文本并记录位置，undo 删除同一段；Invoker 只调用 execute/undo，Receiver 是 Document。价格面板订阅 QuoteFeed 则是观察者：Subject 管理订阅并 notify，Observer 更新视图。若运费在 AirPolicy 与 GroundPolicy 间切换，这是策略；若订单在 Paid 后禁止重复支付，是状态约束。

编辑器例把 Document 定为 Receiver，把 InsertCommand 的位置和文本作为撤销数据；Editor 先调用 execute，成功后才 move 入 history。由此可逐步推出插入、撤销以及越界异常后三种状态。

## 易错点与反例

1. 把客户主动切换运费算法说成状态模式；没有内部状态迁移时策略更直接。
2. Subject 保存 Observer 裸指针却没有退订协议，观察者先销毁后会留下悬空回调。
3. 在 C++ 输出题中忽略对象切片、析构顺序、异常展开或迭代器失效。若片段含未定义行为，就不能声称有确定输出。
4. 看到包装结构就一律回答装饰器。必须以转换接口、增加职责或控制访问的意图区分适配器、装饰器和代理。
