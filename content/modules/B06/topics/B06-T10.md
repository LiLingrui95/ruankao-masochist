# UML综合案例

> 代码基线：C++17；UML 记法按 UML 2.5.1。后续版本特性会明确标注，本节不依赖未指定行为。

## 考查目标

能够准确识别UML综合案例中的角色、约束与边界；能从题干材料推导唯一结论，并说明结论成立的前提。

## 必要概念

综合 UML 建模从需求句中的名词、动词、数量词和生命周期入手。先划系统边界与参与者目标，再建立领域类、属性和关系；随后为关键场景画顺序图，用消息验证类是否拥有相应职责；最后对生命周期复杂的实体画状态机。四种视图应互相校验：顺序图消息应落到某个类的操作，状态迁移应由需求中存在的事件触发，多重性应与业务数量约束一致。

## 原理与条件

综合建模先从需求建立可追踪表：名词候选类，数量词约束多重性，销毁与共享规则决定聚合语义，动词候选消息或状态事件。类图给出静态责任后，用顺序图验证每条消息是否能由接收类承担；用状态机验证实体是否允许该事件。不同图不是独立答案，消息与迁移必须一致。

例如借阅顺序图中的 `BookCopy.checkout()` 应对应状态机 `Available--checkout→OnLoan`。若顺序图允许未检查可用性就 checkout，或类图把历史 Loan 组合进 BookCopy 导致删除副本时历史消失，模型之间即发生矛盾。部署需求则使用部署图表达节点实例、制品与通信路径，不把运行节点误画成领域类。

## 推导例题

图书借阅系统中 Member 可产生 Loan，BookCopy 在同一时刻最多对应一个 active Loan。顺序图 borrow(copyId) 应让 Boundary 调用 LoanService，再查询 Member 与 BookCopy，校验后创建 Loan 并令副本转为 OnLoan。状态机 Available→OnLoan 由 checkout 触发，OnLoan→Available 由 return 触发。若类图写 BookCopy 组合 Loan，便错误暗示副本销毁必然销毁历史借阅记录；应使用普通关联并保存历史。

对课程案例先逐句标出“一门课至少一章”“章节随课程删除”“学生可多选课程”，再完成类图空白关系。Enrollment 既承载选课时间和成绩，又把 Student—Course 的多对多拆成两个一对多。

## 易错点与反例

1. 顺序图出现 `markPaid`，但状态机没有任何进入 Paid 的迁移，导致视图互相矛盾。
2. 材料未给数量下界却自行写 `1..*`；多重性必须由明确业务约束推出。
3. 在 C++ 输出题中忽略对象切片、析构顺序、异常展开或迭代器失效。若片段含未定义行为，就不能声称有确定输出。
4. 看到包装结构就一律回答装饰器。必须以转换接口、增加职责或控制访问的意图区分适配器、装饰器和代理。
